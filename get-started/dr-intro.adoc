= En savoir plus sur la NetApp Disaster Recovery
:hardbreaks:
:allow-uri-read: 
:icons: font
:imagesdir: ../media/get-started/


[role="lead"]
La reprise après sinistre dans le cloud est un moyen résilient et économique de protéger les workloads contre les pannes de site et les événements de corruption des données. NetApp Disaster Recovery est un service de reprise après sinistre basé sur le cloud qui automatise les workflows de reprise après sinistre pour les workloads VMware et Kubernetes exécutés sur le stockage NetApp. Avec Disaster Recovery, vous pouvez protéger les workloads suivants :

* *Workloads VMware* : workloads basés sur NFS et datastores VMFS (VMware vSphere virtual machine file system) pour iSCSI et FC. Vous pouvez les répliquer vers l’un des emplacements suivants :
+
** Amazon Elastic VMware Service (EVS) avec Amazon FSx for NetApp ONTAP. Pour plus de détails, reportez-vous à link:../reference/evs-deploy-guide-introduction.html["Introduction à la reprise après sinistre avec Amazon Elastic VMware Service et Amazon FSx for NetApp ONTAP"].
** VMware Cloud (VMC) sur AWS avec Amazon FSx for NetApp ONTAP
** Azure VMware Solution avec NetApp Cloud Volumes ONTAP (iSCSI) (Aperçu privé)
** Google Cloud VMware Engine (GCVE) avec Google Cloud NetApp Volumes
** Un autre environnement VMware sur site basé sur NFS et/ou VMFS (iSCSI/FC) avec stockage ONTAP


* *Workloads Kubernetes* : applications exécutées sur vos clusters Kubernetes sur site, y compris les environnements OpenShift Virtualization, qui utilisent le stockage ONTAP géré par Trident. Vous les protégez à l’aide de Trident Protect et les répliquez vers un autre cluster Kubernetes.


Disaster Recovery utilise la technologie ONTAP SnapMirror avec l’orchestration native VMware intégrée ou l’orchestration Trident Protect pour protéger les VM VMware et les images de système d’exploitation sur disque qui leur sont associées, ainsi que les applications Kubernetes, tout en conservant tous les avantages d’efficacité du stockage d’ONTAP. Disaster Recovery utilise ces technologies comme transport de réplication vers le site de reprise après sinistre. Cela permet d’obtenir la meilleure efficacité de stockage du secteur (compression et déduplication) sur les sites principal et secondaire.

[[netapp-console]]
== NetApp Console

La reprise après sinistre est accessible via NetApp Console.

La NetApp Console fournit une gestion centralisée des services de stockage et de données NetApp dans les environnements sur site et cloud à l'échelle de l'entreprise. La console est requise pour accéder aux services de données NetApp et les utiliser. En tant qu'interface de gestion, il vous permet de gérer de nombreuses ressources de stockage à partir d'une seule interface. Les administrateurs de console peuvent contrôler l’accès au stockage et aux services pour tous les systèmes de l’entreprise.

Vous n'avez besoin ni de licence ni d'abonnement pour commencer à utiliser NetApp Console et vous n'encourez des frais que lorsque vous devez déployer des agents Console dans votre cloud pour assurer la connectivité à vos systèmes de stockage ou aux services de données NetApp. Cependant, certains services de données NetApp accessibles depuis la Console sont sous licence ou nécessitent un abonnement.

Apprenez-en davantage sur le https://docs.netapp.com/us-en/console-setup-admin/concept-overview.html["NetApp Console"] .



[[benefits-of-using-disaster-recovery]]
== Avantages de l'utilisation de Disaster Recovery

La reprise après sinistre offre les avantages suivants :

* Expérience utilisateur simplifiée pour la découverte des clusters vCenter et Kubernetes, ainsi que la récupération d'applications avec plusieurs opérations de récupération à un point dans le temps.
* Coût total de possession réduit avec un coût d'exploitation réduit et la possibilité de créer et d'ajuster des plans de reprise après sinistre avec des ressources minimales.
* Préparation continue à la reprise après sinistre avec des tests de basculement virtuel qui ne perturbent pas les opérations.  Vous pouvez tester régulièrement vos plans de basculement DR sans impacter les charges de travail de production.
* Rentabilisation plus rapide grâce à des changements dynamiques dans votre environnement informatique et capacité à les prendre en compte dans vos plans de reprise après sinistre.
* Capacité à gérer à la fois les couches de stockage et virtuelles via l'orchestration back-end d' ONTAP et de VMware en même temps sans avoir besoin d'appliances de serveur virtuel (VSA) qui doivent être déployées et maintenues.
* Protection centrée sur les applications pour les workloads Kubernetes utilisant la même technologie ONTAP SnapMirror, avec l’orchestration Trident Protect. Les transformations de ressources vous permettent d’adapter les workloads à l’environnement de reprise pendant le basculement.
* Les solutions DR pour VMware peuvent nécessiter beaucoup de ressources.  De nombreuses solutions DR répliquent les machines virtuelles au niveau de la couche virtuelle VMware à l’aide de VSA, ce qui peut consommer davantage de ressources de calcul et faire perdre les précieuses efficacités de stockage d’ ONTAP.  Étant donné que Disaster Recovery utilise la technologie ONTAP SnapMirror , il peut répliquer les données des banques de données de production vers le site DR à l'aide de notre modèle de réplication incrémentielle permanente avec toutes les efficacités natives de compression et de déduplication des données d' ONTAP.




[[capabilities-of-disaster-recovery]]
== Capacités de reprise après sinistre

La reprise après sinistre vous permet d'exploiter pleinement plusieurs technologies NetApp pour atteindre les objectifs suivants :

* Répliquez les applications VMware sur votre site de production sur site vers un site distant de reprise après sinistre dans le cloud ou sur site à l'aide de la réplication SnapMirror .
* Répliquez des applications Kubernetes vers un cluster Kubernetes de destination à l’aide de la réplication SnapMirror et de Trident Protect.
* Migrez les workloads VMware de votre site d'origine vers un autre site. La migration des workloads Kubernetes n'est actuellement pas prise en charge.
* Effectuez un test de basculement. Pour les workloads VMware, le service crée des machines virtuelles temporaires. Disaster Recovery crée un nouveau volume FlexClone à partir de l’instantané sélectionné, et un datastore temporaire, soutenu par le volume FlexClone, est mappé aux hôtes ESXi. Ce processus ne consomme pas de capacité physique supplémentaire sur le stockage ONTAP sur site ni sur le stockage FSx for NetApp ONTAP dans AWS. Le volume source d’origine n’est pas modifié et les tâches de réplication peuvent se poursuivre même pendant la reprise après sinistre. Vous pouvez également tester le basculement des workloads Kubernetes et nettoyer les ressources de test par la suite.
* En cas de sinistre, basculez votre site principal à la demande vers le site de reprise d'activité. Pour les workloads VMware, le site de reprise d'activité peut être VMware Cloud on AWS avec Amazon FSx for NetApp ONTAP ou un environnement VMware sur site avec ONTAP. Pour les workloads Kubernetes, vous basculez vers le cluster de destination dans le plan de réplication.
* Une fois le sinistre résolu, effectuez une restauration à la demande du site de reprise après sinistre vers le site principal.
* Regroupez les machines virtuelles, les datastores ou les ressources Kubernetes en groupes de ressources logiques pour une gestion efficace.
* Pour les workloads Kubernetes, utilisez des transformations de ressources pour adapter les applications à l'environnement de reprise lors d'un basculement, ainsi que des scripts pré-instantané ou post-instantané pour gérer la quiescence et la reprise des applications.

== Licences

Vous pouvez utiliser les types de licences suivants :

* Inscrivez-vous pour un essai gratuit de 30 jours.
* Achetez un abonnement à la carte (PAYGO) sur la Marketplace Amazon Web Services (AWS), la Marketplace Azure ou la Marketplace Google Cloud. Cette licence vous permet d’acquérir une licence de capacité protégée fixe sans engagement à long terme.
* Apportez votre propre licence (BYOL), qui est un fichier de licence NetApp (NLF) que vous obtenez auprès de votre représentant commercial NetApp . Vous pouvez utiliser le numéro de série de la licence pour activer le BYOL dans la NetApp Console.


Les licences pour tous les services de données NetApp sont gérées via des abonnements dans la NetApp Console.  Après avoir configuré votre BYOL, vous pouvez voir une licence active pour le service dans la console.

Disaster Recovery est concédé sous licence en fonction du volume de données hébergé sur les volumes ONTAP protégés. Le service détermine quels volumes doivent être pris en compte à des fins de licence en associant les VM protégées à leurs datastores vCenter. Chaque datastore est hébergé sur un volume ONTAP ou une LUN. La capacité utilisée signalée par ONTAP pour ce volume ou cette LUN est utilisée pour déterminer la licence. Le calcul de la licence est effectué de la même manière pour les workloads Kubernetes.

Les volumes protégés peuvent héberger de nombreuses machines virtuelles. Certaines peuvent ne pas faire partie d'un groupe de ressources de reprise après sinistre. Quoi qu'il en soit, le stockage consommé par toutes les machines virtuelles de ce volume ou de ce LUN est pris en compte dans la capacité maximale de la licence.


NOTE: Les frais de reprise après sinistre sont calculés en fonction de la capacité utilisée des datastores sur le site source lorsqu'au moins une machine virtuelle ou une ressource Kubernetes dispose d'un plan de réplication. La capacité d'un datastore basculé n'est pas incluse dans le quota. Pour un service BYOL (Bring Your Own License), si le volume de données dépasse la capacité autorisée, les opérations sont limitées jusqu'à l'obtention d'une licence supplémentaire ou la mise à niveau de la licence via la NetApp Console.

Pour plus de détails sur la configuration des licences pour la reprise après sinistre, reportez-vous à link:../get-started/dr-licensing.html["Configurer la licence NetApp Disaster Recovery"].

[[how-disaster-recovery-works]]
== Comment fonctionne la reprise après sinistre

La reprise après sinistre est un service disponible dans l’environnement software as a service (SaaS) de NetApp Console. La reprise après sinistre peut restaurer des workloads répliqués depuis un site sur site vers Amazon FSx for ONTAP ou vers un autre site sur site. Pour les workloads VMware, ce service automatise la restauration depuis le niveau SnapMirror, jusqu’à l’enregistrement des machines virtuelles sur VMware Cloud on AWS, ainsi que les mappages réseau directement sur la plateforme de virtualisation et de sécurité réseau VMware, NSX-T. Cette fonctionnalité est incluse dans tous les environnements Virtual Machine Cloud.

La reprise après sinistre utilise la technologie ONTAP SnapMirror, qui assure une réplication très efficace et préserve l'efficacité des snapshots incrémentiels permanents d'ONTAP. La réplication SnapMirror garantit que les copies de snapshots cohérentes au niveau des applications sont toujours synchronisées et que les données sont immédiatement utilisables après un basculement.

image:dr-architecture-diagram-70-2.png["Diagramme illustrant l'architecture de l'infrastructure du service de reprise après sinistre"]

En cas de sinistre, ce service vous aide à récupérer des machines virtuelles VMware dans l'autre environnement VMware sur site ou VMC en rompant les relations SnapMirror et en rendant le site de destination actif.

* Le service vous permet également de restaurer les machines virtuelles à l’emplacement source d’origine.
* Vous pouvez tester le processus de basculement de reprise après sinistre sans perturber les machines virtuelles d'origine.  Le test récupère les machines virtuelles sur un réseau isolé en créant un FlexClone du volume.
* Pour le processus de basculement ou de test de basculement, vous pouvez choisir le snapshot le plus récent (par défaut) ou sélectionné à partir duquel récupérer votre machine virtuelle.


*workloads Kubernetes*

Pour les workloads Kubernetes, Disaster Recovery utilise Trident Protect pour protéger les applications exécutées sur vos clusters Kubernetes, y compris les environnements de virtualisation OpenShift. Le service utilise SnapMirror pour répliquer les volumes persistants que NetApp Trident provisionne sur le stockage ONTAP. Trident Protect enregistre les données de protection Kubernetes dans un AppVault, qui est une cible de stockage cloud. En cas de sinistre, vous basculez vers le cluster de destination, et vous pouvez revenir au cluster source d'origine une fois le sinistre résolu. Le basculement, le retour arrière et le test de basculement pour les workloads Kubernetes suivent la même séquence que pour les workloads VMware.

*Composants de la reprise après sinistre*

La reprise après sinistre utilise les composants suivants :

* * NetApp Console* : L'interface utilisateur pour la gestion de vos plans de reprise après sinistre.  Vous pouvez utiliser la NetApp Console pour créer et gérer des plans de réplication, des groupes de ressources et des opérations de basculement dans vos environnements locaux et cloud.
* *Console agent* : composant logiciel léger qui s’exécute dans votre réseau hébergé dans le cloud ou dans votre environnement VMware sur site. Il communique avec la NetApp Console et gère la réplication des données entre votre environnement sur site et le site de reprise d’activité. Le Console agent est installé sur une machine virtuelle dans votre environnement VMware. Pour les workloads Kubernetes, le Console agent communique de la même manière avec vos clusters Kubernetes.
* *Clusters de stockage ONTAP* : Les clusters de stockage ONTAP sont les principaux systèmes de stockage qui hébergent vos workloads VMware et Kubernetes. Les clusters de stockage ONTAP fournissent l’infrastructure de stockage sous-jacente à vos plans de reprise d’activité. Disaster Recovery utilise les API de stockage ONTAP pour gérer les clusters de stockage ONTAP, tels que les baies sur site et les solutions basées sur le cloud, comme Amazon FSx for NetApp ONTAP.
* *Serveurs vCenter* : VMware vCenter est le serveur de gestion de votre environnement VMware.  Il gère les hôtes ESXi et leurs banques de données associées.  L'agent de console communique avec VMware vCenter pour gérer la réplication des données entre votre environnement local et le site de reprise après sinistre.  Cela inclut l’enregistrement des LUN et des volumes ONTAP en tant que banques de données, la reconfiguration des machines virtuelles et le démarrage et l’arrêt des machines virtuelles.
* *Kubernetes clusters and Trident Protect*: Pour les workloads Kubernetes, Trident Protect est installé et enregistré sur chaque cluster Kubernetes que Disaster Recovery protège. Lorsque vous ajoutez un cluster Kubernetes comme site, Disaster Recovery vous guide tout au long de l’installation et de l’enregistrement de Trident Protect sur ce cluster.


*Le flux de travail de protection de reprise après sinistre*

Lorsqu'un plan de réplication est attribué à un groupe de ressources, Disaster Recovery effectue une vérification de découverte de tous les composants du groupe de ressources et du plan pour garantir que le plan peut être activé.

Si cette vérification réussit, Disaster Recovery exécute les étapes d'initialisation suivantes :

. Pour chaque machine virtuelle du groupe de ressources cible, identifiez la banque de données VMware hébergeante.
. Pour chaque banque de données VMware trouvée, identifiez le volume ou le LUN ONTAP FlexVol volume d'hébergement.
. Pour chaque volume ONTAP et LUN trouvés, déterminez s'il existe une relation SnapMirror entre les volumes sources et un volume de destination sur le site de destination.
+
.. S'il n'existe aucune relation SnapMirror préexistante, créez de nouveaux volumes de destination et créez une nouvelle relation SnapMirror entre chaque volume source non protégé.
.. S'il existe une relation SnapMirror préexistante, utilisez cette relation pour effectuer toutes les opérations de réplication.




Une fois que Disaster Recovery a créé et initialisé toutes les relations, à chaque sauvegarde planifiée, le service exécute les étapes de protection des données suivantes :

. Pour chaque machine virtuelle marquée comme « cohérente au niveau de l’application », utilisez VMware Tools pour placer l’application prise en charge dans un état de sauvegarde.
. Créez un nouvel instantané de tous les volumes ONTAP hébergeant des banques de données VMware protégées.
. Effectuez une opération de mise à jour SnapMirror pour répliquer ces snapshots sur le cluster ONTAP de destination.
. Déterminez si le nombre de snapshots conservés a dépassé la rétention maximale de snapshots définie dans le plan de réplication et supprimez tous les snapshots superflus des volumes source et de destination.




[[supported-protection-targets-and-datastore-types]]
== Cibles de protection et types de banques de données pris en charge

*Types de datastore pris en charge* Disaster Recovery prend en charge les types de datastore suivants :

* Banques de données NFS hébergées sur des volumes ONTAP FlexVol résidant sur des clusters ONTAP .
* Banques de données du système de fichiers de machine virtuelle VMware vSphere (VMFS) utilisant le protocole iSCSI ou FC


Pour les charges de travail Kubernetes, la reprise après sinistre protège les volumes persistants provisionnés via NetApp Trident sur le stockage ONTAP.

*Cibles de protection prises en charge*

* VMware Cloud (VMC) sur AWS avec Amazon FSx for NetApp ONTAP
* Un autre environnement VMware sur site, basé sur NFS avec un stockage ONTAP, ou un environnement VMFS FC/iSCSI sur site
* Service VMware élastique Amazon
* Azure VMware Solution avec NetApp Cloud Volumes ONTAP (iSCSI) (Aperçu privé)
* Google Cloud VMware Engine (GCVE) avec Google Cloud NetApp Volumes
* Clusters Kubernetes exécutant un stockage ONTAP géré par Trident (protégé à l'aide de Trident Protect)




[[terms-that-might-help-you-with-disaster-recovery]]
== Termes pouvant vous aider en matière de reprise après sinistre

Il pourrait être utile de comprendre certains termes liés à la reprise après sinistre.

* *Datastore* : un conteneur de données VMware vCenter, qui utilise un système de fichiers pour contenir les fichiers VMDK.  Les types de banques de données typiques sont NFS, VMFS, vSAN ou vVol.  Disaster Recovery prend en charge les banques de données NFS et VMFS.  Chaque banque de données VMware est hébergée sur un seul volume ONTAP ou LUN.  Disaster Recovery prend en charge les banques de données NFS et VMFS hébergées sur des volumes FlexVol résidant sur des clusters ONTAP .
* *Plan de réplication* : un ensemble de règles sur la fréquence des sauvegardes et sur la manière de gérer les événements de basculement.  Les plans sont attribués à un ou plusieurs groupes de ressources.
* *Objectif de point de récupération (RPO)* : La quantité maximale de perte de données acceptable en cas de sinistre.  Le RPO est défini dans la fréquence de réplication des données ou dans le calendrier de réplication du plan de réplication.
* *Objectif de temps de récupération (RTO)* : durée maximale acceptable pour la reprise après sinistre. Le RTO est défini dans le plan de réplication et correspond au temps nécessaire pour basculer vers le site de reprise après sinistre et redémarrer toutes les machines virtuelles ou applications.
* *Groupe de ressources* : conteneur logique qui vous permet de gérer plusieurs machines virtuelles, datastores ou ressources Kubernetes comme une seule unité. Une machine virtuelle ne peut appartenir qu’à un seul groupe de ressources à la fois. Vous pouvez créer un groupe de ressources pour chaque application ou workload que vous souhaitez protéger.
* *Site* : conteneur logique généralement associé à un centre de données physique ou à un emplacement cloud hébergeant un ou plusieurs clusters vCenter ou Kubernetes, ainsi qu’un stockage ONTAP.
* *AppVault* : pour les workloads Kubernetes, un stockage cloud cible dans lequel Trident Protect enregistre les données de protection Kubernetes.
* *Trident Protect* : logiciel NetApp utilisé par Disaster Recovery pour protéger les applications Kubernetes.
