[[google-cloud-prerequisites-and-considerations]]
== Prérequis et considérations relatifs à Google Cloud

Lorsque vous utilisez NetApp Disaster Recovery avec Google Cloud VMware Engine et Google Cloud NetApp Volumes, assurez-vous de configurer les autorisations appropriées et examinez les considérations suivantes.

* Contactez l'équipe SRE de Google pour ajouter les éléments suivants à la liste blanche :
+
** API de synchronisation pour transférer les instantanés du stockage sur site vers Google Cloud NetApp Volumes.
** le projet Google avec le moteur VMware pour la création, le montage et le démontage de banques de données.


* Vous devezlink:https://docs.google.com/forms/d/1zuaHu437MNpUf8i5oByK-OTLWXcNIg0es9t036riYRc/viewform?edit_requested=true["Déposez une demande pour ajouter vos volumes à la liste blanche en matière de réplication hybride."^] .
* Soyez conscient delink:https://docs.cloud.google.com/netapp/volumes/docs/quotas["Quotas et limites de Google Cloud NetApp Volumes"^] .
* Vous ne pouvez ajouter qu'un seul volume ou une seule banque de données à un plan de réplication.
* Examinerlink:../release-notes/dr-limitations.html#limitations-with-google-cloud-netapp-volumes["limites"] .


**Considérations relatives au basculement**

* Le basculement n'est pris en charge qu'avec le dernier instantané. Si nécessaire, vous pouvez créer un nouvel instantané pendant le basculement (c'est-à-dire que l'option d'instantané sélectif doit être désactivée).
* Il est impossible de créer un nouvel instantané après un basculement.
* Il est impossible de conserver et de réconcilier les instantanés après un basculement.


**Considérations relatives aux solutions de repli**

* La restauration n'est possible qu'avec l'option de capture d'écran sélective.  Il est impossible d'effectuer une restauration en prenant un nouvel instantané.
* Si vous supprimez le peering de cluster entre le stockage sur site et les clusters de stockage Google Cloud NetApp Volumes , vous devez supprimer manuellement l'entrée de peering de cluster et de machine virtuelle de stockage du cluster sur site. Pour plus d'informations, voir link:https://docs.netapp.com/us-en/ontap-cli/vserver-peer-delete.html["Supprimer une relation d'homologue vserver"^].

[[ontap-storage-prerequisites]]
== Prérequis de stockage ONTAP

Ces prérequis s'appliquent aux instances ONTAP et Amazon FSx for NetApp ONTAP.

* Les clusters source et de destination doivent avoir une relation d'homologue.
* La SVM qui héberge les volumes de reprise après sinistre doit exister sur le cluster de destination.
* La SVM source et la SVM de destination doivent avoir une relation homologue.
* link:task-kubernetes-requirements.html["Consultez les exigences supplémentaires pour les clusters Kubernetes"].
* En cas de déploiement avec Amazon FSx for NetApp ONTAP, la condition préalable suivante s'applique :
+
** Une instance Amazon FSx for NetApp ONTAP pour héberger les magasins de données VMware DR doit exister dans votre VPC. Pour commencer, voirlink:https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/getting-started-step1.html["la documentation Amazon FSx pour ONTAP"^] .

[[create-the-netapp-console-agent]]
=== Créer l'agent de la NetApp Console

L’agent Console est un composant logiciel qui permet à la Console de communiquer avec votre stockage ONTAP et vos clusters VMware vCenter ou vos clusters Kubernetes. Il est nécessaire au bon fonctionnement de Disaster Recovery. L’agent réside dans votre réseau privé (soit un centre de données sur site, soit un VPC cloud) et communique avec vos instances de stockage ONTAP ainsi qu’avec tous les composants de serveur et d’application supplémentaires. Pour Disaster Recovery, cela correspond à l’accès à vos clusters vCenter gérés ou à vos clusters Kubernetes.

Un agent de console doit être configuré dans la NetApp Console.  Lorsque vous utilisez l’agent, il inclura les fonctionnalités appropriées pour le service de reprise après sinistre.

* La reprise après sinistre fonctionne uniquement avec le déploiement de l'agent en mode standard. Voir https://docs.netapp.com/us-en/console-setup-admin/task-quick-start-standard-mode.html["Prise en main de la NetApp Console en mode standard"^].
* Assurez-vous que les clusters vCenter source et de destination, ou les clusters Kubernetes, utilisent le même Console agent.
* Type d'agent de console requis :
+
** *Reprise après sinistre sur site à site* : Installez l’agent Console local sur le site de reprise après sinistre. Grâce à cette méthode, une panne du site principal n’empêche pas le service de redémarrer vos ressources virtuelles sur le site de reprise après sinistre. Reportez-vous à https://docs.netapp.com/us-en/console-setup-admin/task-install-connector-on-prem.html["Installer et configurer l'agent de console sur site"^].
+
La reprise après sinistre prend également en charge l'utilisation de plusieurs agents de console avec des configurations sur site. Dans ce scénario, les agents de la console dirigent les actions vers les vCenters et les clusters de baies ONTAP , et la source et la cible auraient chacune leur propre agent de console. L'utilisation de plusieurs agents Console est recommandée pour réduire la latence et améliorer le temps de récupération en cas de défaillance d'un agent Console ou d'un site.

** *Sur site sur AWS* : installez l’agent de console pour AWS dans votre AWS VPC. Se référer à https://docs.netapp.com/us-en/console-setup-admin/concept-install-options-aws.html["Options d'installation de l'agent de console dans AWS"^] .
+

TIP: Pour les connexions sur site vers sur site, utilisez l’agent de console sur site.  Pour les connexions sur site vers AWS, utilisez l'agent de la console AWS, qui a accès au vCenter sur site source et au vCenter sur site de destination.

** L’agent Console installé doit pouvoir accéder à tous les clusters Kubernetes que Disaster Recovery gérera. Il doit également pouvoir accéder à toutes les instances de cluster VMware vCenter et aux hôtes ESXi gérés par ces clusters vCenter que Disaster Recovery gérera.


* Toutes les baies ONTAP qui doivent être gérées par Disaster Recovery doivent être ajoutées à n'importe quel système du projet NetApp Console qui sera utilisé pour gérer Disaster Recovery.
+
Voir https://docs.netapp.com/us-en/storage-management-ontap-onprem/task-discovering-ontap.html["Découvrez les clusters ONTAP sur site"^] .

* Pour plus d'informations sur la configuration d'un proxy intelligent pour la reprise après sinistre, consultez link:../get-started/dr-setup.html["Mettez en place votre infrastructure de reprise après sinistre"].




[[workload-prerequisites]]
== Prérequis de charge de travail

Pour garantir la réussite des processus de cohérence au niveau des applications pour les workloads VMware, appliquez les prérequis suivants :

* Assurez-vous que les outils VMware (ou les outils Open VM) sont en cours d’exécution sur les machines virtuelles qui seront protégées.
* Pour les machines virtuelles Windows exécutant Microsoft SQL Server, Oracle Database ou les deux, les bases de données doivent avoir leurs rédacteurs VSS activés.
* Les bases de données Oracle exécutées sur un système d'exploitation Linux doivent avoir l'authentification utilisateur du système d'exploitation activée pour le rôle SYSDBA de la base de données Oracle.



IMPORTANT: En fonction de votre type de déploiement, examinez le link:reference-vmware-prerequisites.html["Prérequis pour un cluster VMware"] et le link:task-kubernetes-requirements.html["Prérequis pour un cluster Kubernetes"].
